# 🗄️ Enterprise Database Integration (SQLAlchemy)

`OpenLocalRagAgents` features a modular, database-agnostic connector layer (`src/connectors/`) built on **SQLAlchemy**. It enables plug-and-play connectivity to **PostgreSQL, MSSQL, MySQL, Oracle, or SQLite** without coupling to proprietary database vendor APIs.

---

## 🎯 Integration Patterns

The system supports two complementary database workflows:

1. **Live Text-to-SQL (`db_agent`):**
   - Designed for numeric, transactional, and dynamic operational data (sales, inventory, orders).
   - The `db_agent` specialist reads the accessible schema, has the LLM write a single read-only `SELECT`, executes it through the security guard below, and summarizes the rows. Recent conversation turns are included, so follow-ups such as *"What is its unit price?"* work.
   - The supervisor routes database questions to `db_agent` automatically, or clients can force it with `"agent": "db_agent"` on `/api/v1/query`.
2. **Table-to-Vector ETL Synchronization:**
   - Extracts text columns (support tickets, CRM notes, product descriptions), adds a contextual record header, and indexes each row into ChromaDB so `doc_agent` can retrieve it semantically.

## ⚙️ Configuration (`.env` or Environment Variables)

Connect any relational database by defining a single `DATABASE_URL` environment variable:

```env
# 1. PostgreSQL
DATABASE_URL=postgresql+psycopg2://user:password@localhost:5432/enterprise_db

# 2. Microsoft SQL Server (MSSQL)
DATABASE_URL=mssql+pyodbc://user:password@host:1433/enterprise_db?driver=ODBC+Driver+17+for+SQL+Server

# 3. MySQL
DATABASE_URL=mysql+pymysql://user:password@localhost:3306/enterprise_db

# 4. Oracle
DATABASE_URL=oracle+cx_oracle://user:password@localhost:1521/?service_name=enterprise_db

# 5. SQLite
DATABASE_URL=sqlite:///./data/sample_enterprise.db

# Empty (default): use the auto-generated sample database (see below)
DATABASE_URL=
```

> [!NOTE]
> Database drivers are not bundled in `requirements.txt`. Install the one for your database, e.g. `pip install psycopg2-binary` (PostgreSQL), `pymysql` (MySQL), `pyodbc` (MSSQL), or `cx_Oracle` / `oracledb` (Oracle).

### Access Scope & Limits

```env
# Allow access only to explicit business tables (empty = all tables):
DB_ALLOWED_TABLES=urunler,satislar,destek_talepleri

# Maximum number of rows returned per query (default: 50):
DB_MAX_ROWS=50

# Statement timeout for PostgreSQL / MySQL queries in seconds (default: 15):
DB_QUERY_TIMEOUT_SECONDS=15
```

> [!IMPORTANT]
> **Use a SELECT-only database account in production.** The guards below are defense in depth, but database privileges are the only protection that no query can get around. This matters most for MSSQL and Oracle, where no session-level read-only mode is applied automatically.

---

## 🔒 Strict Read-Only Security Guard

Every query, whether generated by `db_agent`, sent to `/api/v1/database/test-query`, or issued by the ETL loader, passes through `DatabaseConnector.execute_query()` (`src/connectors/db_connector.py`):

1. **Single Statement:** The query is split with `sqlparse`; anything other than exactly one statement is rejected (`SELECT 1; DROP TABLE users` → rejected, including when comments are placed between statements).
2. **Forbidden Keywords (token-level):** The parsed tokens are scanned for data-, schema-, session-, and file-modifying keywords: `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `CREATE`, `MERGE`, `UPSERT`, `INTO` (blocks `SELECT … INTO`), `EXEC`/`EXECUTE`, `CALL`, `COPY`, `GRANT`, `REVOKE`, `ATTACH`/`DETACH`, `PRAGMA`, `SET`, `LOCK`, `LOAD`, `OUTFILE`/`DUMPFILE`, transaction control (`BEGIN`, `COMMIT`, `ROLLBACK`, …) and more. String literals are skipped, so `WHERE status = 'Deleted'` is allowed.
3. **Forbidden Functions:** Calls that read or write files, reach the network, stall the server, or change server state are rejected, e.g. `pg_read_file`, `pg_ls_dir`, `lo_import`, `dblink`, `pg_sleep`, `pg_terminate_backend`, `load_extension`, `load_file`, `sleep`, `benchmark`, `xp_cmdshell`, `openrowset`, and any `dbms_*` / `utl_*` package call.
4. **Statement Type:** The statement must start with `SELECT` or `WITH`.
5. **Table Allowlist (`DB_ALLOWED_TABLES`):** All referenced tables are extracted from `FROM` lists (including comma joins such as `FROM a, b`), every `JOIN` variant, subqueries, and CTE bodies. Quoted (`"table"`) and schema-qualified (`schema.table`) names are normalized; CTE names defined in the query are allowed. With an allowlist in place, system catalogs such as `sqlite_master` or `information_schema` are rejected too. Without `DB_ALLOWED_TABLES`, every table the database account can see is queryable.
6. **Database-Enforced Read-Only Session:**
   | Dialect | Enforcement |
   | :--- | :--- |
   | SQLite | `PRAGMA query_only = ON` on every connection (the engine rejects all writes) |
   | PostgreSQL | `SET TRANSACTION READ ONLY` + `SET LOCAL statement_timeout` per query |
   | MySQL / MariaDB | `SET SESSION TRANSACTION READ ONLY` (session scope, so DDL cannot escape via implicit commit) + session execution time limit |
   | MSSQL / Oracle | None automatically; a warning is logged. Use a SELECT-only account. |

   Each query's transaction is rolled back after the rows are fetched.
7. **Row Capping:** Result sets are capped at `DB_MAX_ROWS`.
8. **Error Messages:** Guard rejections return a descriptive `Security Guard: …` message. Database execution errors return only the error type; details go to the server log.

**ETL Loader Identifier Sanitization:** `DatabaseTableLoader.load_table_as_chunks()` only accepts a `table_name` that is a valid identifier and appears in the accessible table list (`get_tables()`, which honors `DB_ALLOWED_TABLES`).

## 🔄 Table Vectorization (ETL Sync)

Synchronize a relational table into ChromaDB using either the Web UI or REST API. Each row becomes one chunk with a header such as:

```text
[Database Table: destek_talepleri | Record: #1 | Server BIOS Update]
konu: Server BIOS Update
detay: IPMI disconnected after Enterprise Server X1 reboot.
cozum: Applied IPMI firmware 2.14 patch and reset static IP.
```

Re-syncing a table replaces all of its previously indexed rows, so rows deleted from the database also disappear from the index.

### Via the web UI (admin):
1. Open **Administration → System**. The **Database** card shows the connection and its tables.
2. Type the table name (e.g., `destek_talepleri`) and click **"Sync table into the index"**. All columns are indexed.

The same card runs read-only test queries.

### Via REST API:
> [!NOTE]
> Requires `Authorization: Bearer <token>` with `admin` role.

```bash
curl -X POST "http://localhost:8000/api/v1/database/sync-table" \
     -H "Authorization: Bearer <admin_token>" \
     -H "Content-Type: application/json" \
     -d '{
       "table_name": "destek_talepleri",
       "text_columns": ["konu", "detay", "cozum"],
       "title_column": "konu",
       "id_column": "talep_id"
     }'
```

## 🧪 Zero-Config Sample Database (`sample_enterprise.db`)

When `DATABASE_URL` is empty, the platform generates `data/sample_enterprise.db` on the first start and connects to it immediately, so database features work right after cloning.

Pre-populated mock enterprise datasets include:
- **`urunler` (Products):** `urun_id`, `sku`, `urun_adi`, `kategori`, `birim_fiyat`, `stok_adedi`.
- **`satislar` (Sales):** `satis_id`, `siparis_no`, `musteri_adi`, `urun_id`, `adet`, `toplam_tutar`, `bolge`, `tarih`.
- **`destek_talepleri` (Support Tickets):** `talep_id`, `talep_kodu`, `musteri_adi`, `konu`, `detay`, `cozum`, `durum`.
